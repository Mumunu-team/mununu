# Auto-Extraction × Real-Upstream-Bug Gap Analysis

> **Status: scope statement.** This document records the result of a 2026-05-18 audit
> against a specific, narrow question. It does not change behaviour and does not propose
> work; it documents what is and is not currently demonstrable. Paralleling the role
> of the C-extractor scoping log at
> `c-extraction-llvm-lift.md` (a planning note, not tracked).

## Question

Does the mununu repository contain at least one example that satisfies **both** of the
following conditions simultaneously?

1. **Auto-extracted.** The CTXDSL model is produced by an automated extraction pipeline
   (`mununu codesign extract-c`, `mununu-extract ast`, an extraction-spec → CTXDSL
   generator, or an equivalent path) — no hand-authoring of the model file.
2. **Real upstream bug.** The bug detected by the property is a documented, real defect
   in the upstream source from which the model was extracted — not a deliberately
   introduced ("planted") demonstration bug, and not a property-class study without a
   concrete upstream defect.

Both conditions must hold on the same example. Hand-authored protocol specs that
serve as the *property* (what correctness looks like) are permitted; the *bug-bearing
model* must come from extraction.

## Audit method

Five candidates evaluated against the public repo (`mununu` at branch
`feat/firmware-cve-redfish-auth-example`, commit `9f3fde4`, 2026-05-18). Budget set at
five candidates; stop on exhaustion. No new models or bugs introduced during the audit.

## Verdict

**Zero of five candidates satisfy both conditions.** Audit stops per the five-candidate
budget. No further candidates were evaluated; the report does not speculate about
hypothetical targets that have not been verified.

## What this means

### What mununu's auto-extraction stack actually does today

- **`mununu codesign extract-c` on self-contained C source**: shipped, real-clang
  end-to-end. Proven on `examples/industrial/codesign_uart/firmware.c` and
  `examples/industrial/codesign_nrf52_twim_i2c/firmware.c` /
  `firmware_buggy.c`. Phase status (L2 shipped, L3 onwards in progress) is tracked in
  `c-extraction-llvm-lift.md` (a planning note, not tracked).
- **`mununu-extract ast`** (tree-sitter, Python / TypeScript / Rust / Go): produces
  `.espec.json` extraction specs, not CTXDSL directly. The downstream
  `ExtractionAdapter` consumes those specs. Examples in `examples/ast_extract/stubs/`
  are stubs; no real end-to-end demonstration of bug-bearing source.
- **SystemVerilog**: the adapter is a Kripke builder, not an extractor. It consumes
  `.sv` + `.mununu.json` sidecars; the *modelling* step is human authoring.
- **CrewAI / LangGraph / XState / microcode JSON adapters**: format translators for
  pre-existing model descriptions. Not source-code extractors.
- **AIGER / TLSF / Promela / BTOR2**: pre-existing model formats. Not extraction.

### What is NOT yet demonstrated end-to-end

- **`extract-c` against upstream source that requires an SDK include tree.** Surfaced
  honestly in the nRF52 README: extraction failed against `nrfx_twim.c`, mitigated by
  re-authoring a self-contained `firmware.c` with literal MMIO addresses. The gap is
  a `--include-stub` mode (or an SDK-ingestion recipe). No open plan today.
- **Publicly-auditable `.espec.json` → CTXDSL extraction** for TypeScript / Python /
  Go targets. The MCP CVE examples' generator lives in `mununu-private/`; reviewers
  cannot replay the extraction. Whether to publish the generator is a private/public
  boundary question, not a technical one.
- **Auto-extraction from RTL** at a granularity sufficient to model upstream bugs
  like Caliptra-RTL #150. The RTL-002 staging example is hand-authored modelling, not
  extraction.
- **Any end-to-end demonstration in which an automated pipeline ingests a real public
  codebase and the resulting model exhibits a documented upstream defect.** This is
  the gap the audit set out to find. It is not closed.

### Distance to a valid PoC

A realistic, non-hallucinated estimate of what would have to land before condition
(1) AND condition (2) can both be satisfied on a real artifact:

| Requirement | Today | Effort estimate (informed by the c-extraction scoping log) |
|---|---|---|
| Identify a real, public CVE in a small, self-contained C file (no SDK ingestion needed) | Not yet identified in this audit | Hours of targeted CVE search; no guarantee one exists in the L2-tractable shape |
| `extract-c` produces CTXDSL of the bug-bearing function | Works on the `firmware.c` / `firmware_buggy.c` shape | Already shipped *if* the candidate fits the shape |
| Composition with a hand-authored property spec | Pattern exists (`codesign_uart/extract_verify_recipe/`) | Hours per target |
| `mununu verify` reports a violation with a counterexample lasso | Works on the codesign examples | Already shipped (A3) |
| Verilator reproduction under `hw-verif:latest` | Pattern exists at `examples/verify/sv_yosys_caliptra_rtl_150/` for RTL; not applicable to firmware C | N/A for the C path |
| **OR** ship `--include-stub` mode + ingest a real upstream CVE-bearing firmware file | Not in any open plan | Multi-week if scoped seriously |
| **OR** publish the TS/Python extraction generator + reproducible specs | Tooling is private | Policy decision before engineering |
| **OR** ship RTL-extraction sufficient to model Caliptra-class targets | Out of current adapter scope | Multi-quarter |

The shortest credible path is the first row group: **find a small, self-contained C
file in a public codebase that carries a documented CVE and fits the L2 extractor's
shape (literal MMIO addresses, no SDK headers, single function or two-function chain
within L5 reach)**. This is an empirical question — it requires searching public CVE
databases for matching candidates and confirming the extractor handles each one. The
audit did not perform that search, and does not assert any specific candidate would
succeed; absent that empirical evidence the answer to the audit question is "not
today, and the closing-the-gap step is bounded by what public CVEs the L2 extractor
can ingest, not by mununu engineering effort".

## What this analysis is *not*

- It is not a claim that mununu cannot find real bugs in real systems. The
  verification machinery is sound for the property classes covered by the soundness
  matrix in [`docs/abstraction.md`](../abstraction.md); the gap is that we have not
  *demonstrated* this end-to-end with an automated extraction pipeline against a
  documented upstream defect.
- It is not a negative assessment of the planted-demo examples. Those serve a
  legitimate purpose — they demonstrate the verification, composition, and
  counterexample machinery on controlled property classes, and they are honestly
  disclosed as demos per [Claims Integrity Rule 2](../policies/claims-integrity.md).
- It is not a proposal to ship anything. It is a status statement. Any work to close
  the gap should be planned, scoped, and tracked through the usual plan files in
  `plans/` or `scoping-logs` (a planning note, not tracked).
