# Agentic RTL loop — sound control-kernel synthesis + whole-system verification

A reproducible demo of the mununu loop for control-heavy RTL: the **datapath
sub-modules are hand/LLM-written SystemVerilog**, but the **control kernel is
synthesized correct-by-construction** from a spec, and mununu then **verifies the
whole assembled system** — including that the sub-modules satisfy the kernel's
assumptions.

The example is a **2-client bus arbiter**: the textbook GR(1) synthesis problem
(mutual exclusion + no starvation), dropped into a small system with two concrete
bus masters.

## The loop

```
requirement.md  ──prompt.md──▶  arbiter.tlsf  ──mununu synth──▶  gr1_controller.sv
   (English)        (LLM)          (spec)        (sound GR(1))     (correct-by-construction RTL)
                                                                        │
   master.sv (LLM-authored datapath)  ───────────assemble────────────▶ system.sv
                                                                        │
                                                            mununu verify (yosys+btormc)
                                                                        ▼
                                          mutex ✓  no-starvation ✓  assumptions discharged ✓
```

The LLM owns the two English→artifact steps (the datapath SV and the spec draft);
mununu owns the two formal steps (sound synthesis and whole-system verification).

## The pieces

| File | Role | Who writes it |
|---|---|---|
| `requirement.md` | the plain-English control requirement | the designer / upstream agent |
| `prompt.md` | the reusable NL → TLSF prompt (first leg of the loop) | the loop |
| `arbiter.tlsf` | the control-kernel spec | the LLM, via `prompt.md` |
| `master.sv` | a bus master (latches a request, holds it until granted) | LLM-authored datapath |
| `system.sv` | the top: two masters + the arbiter + verification monitors | assembly |
| `gr1_controller.sv` | the **synthesized** arbiter | **mununu** (generated by `run.sh`) |
| `run.sh` / `verify.sh` | synthesize → assemble → verify | the loop |
| `arbiter_3client.tlsf` | a fresh 3-client requirement, to show the loop generalizes | the LLM |

## Run it

```bash
./run.sh          # needs `mununu` on PATH + the mununu-sva docker image
```

The first leg — `requirement.md` + `prompt.md` → `arbiter.tlsf` — is the LLM's job
(a GenAI-RTL agent runs it); the checked-in `arbiter.tlsf` is its output. `run.sh`
picks up from the spec:

1. **Synthesizes** the arbiter from `arbiter.tlsf` with the sound GR(1) engine
   (`mununu context synth --controller-mode gr1 --emit-sv gr1_controller.sv`).
   The emitted controller *cannot* violate mutual exclusion or fairness — it is
   correct by construction.
2. **Assembles** `master.sv` + `system.sv` + the synthesized `gr1_controller.sv`.
3. **Verifies the whole system** (yosys → BTOR2 → `btormc`, in the `mununu-sva`
   image), by k-induction.

## What is verified (and why it matters)

All five monitors come back `unsat` (property holds), each by k-induction:

- `bad_mutex` — the arbiter's **mutual exclusion** guarantee, checked in the
  assembled system (never `grant_0 & grant_1`).
- `bad_starve_0`, `bad_starve_1` — **no starvation** for each client (a pending
  request is served within a bounded number of cycles). This is a *liveness*
  property; it is k-induction-provable here precisely **because** the concrete
  masters constrain the environment — the assume-guarantee payoff.
- `bad_proto_0`, `bad_proto_1` — the masters **discharge the arbiter's
  assumption** (each holds its request until granted, the protocol the synthesized
  arbiter relies on).

So the soundness argument closes compositionally:

> the kernel satisfies its guarantees **under** its assumptions (by synthesis) →
> the masters **discharge** those assumptions (verified) → the masters' own
> behavior holds (verified) → **the whole system is correct**.

Each leg is independently machine-checked; no leg rests on human reasoning.

## Negative control

The verification is not vacuous. Swap the synthesized arbiter for a broken one
that grants whoever requests (no mutex), and `bad_mutex` becomes **`sat`** — the
check discriminates.

## Generality — the loop is not hardcoded

The same prompt and the same synthesizer scale: `arbiter_3client.tlsf` is a fresh
**3-client** requirement (three request/grant pairs, pairwise mutex, three
no-starvation guarantees). `mununu … --controller-mode gr1` synthesizes it (a
73-state game, memoryful round-robin over 3 modes), and `btormc` **proves the
3-way mutual exclusion** (k-induction) with no starvation counterexample for any
client. Nothing about the pipeline is specific to two clients.

## The productized verb

`run.sh` uses `btormc` directly (a mununu engine) so it can check *every* property
— including the combinational grants and the liveness monitors — in one place.
The headline no-sidecar verb, `mununu sv verify-auto`, is also wired:

```bash
./verify_auto.sh
#   verify-auto: 1 property verified, 0 unsupported assertion(s)
#     model: 6 state register(s)
#     [assert] system_checked_sva_0: HOLDS
```

`system_checked.sv` writes the arbiter's mutual-exclusion guarantee as an SVA over
*registered* grants, so verify-auto's predicate-abstraction path binds it and
proves it **HOLDS** (a definite, sound verdict) on the assembled design. (verify-auto's
cube path only binds *state* atoms, which is why the full-coverage `run.sh` uses
explicit state monitors for the combinational/liveness properties.)

## Honest scope

- This is a **constructed demo system**, not a finding about a real chip.
- The arbiter is in the **GR(1) reactive-control fragment** (mutex + response
  guarantees) — the sweet spot for sound synthesis, and where LLM-written control
  logic is most error-prone. It is not full-LTL or datapath synthesis.
- The **NL → TLSF leg is done by an LLM** (`prompt.md`); the checked-in `.tlsf`
  files are example outputs. mununu owns the synthesis and verification legs.
- Verification here uses `btormc` (a mununu engine) directly on the lifted design;
  the productized verbs are `mununu sv verify-auto` and `mununu btor2 verify`.
