### Why this matters more than the raw numbers suggest

The SoA migration was sold (in EXP-0002 README) on TWO axes: wall-clock AND heap. EXP-0002b confirmed the wall-clock axis at 2.4× on grid_32x32. EXP-0002b-mem now refutes the heap axis at the same scale. **The win is real but the mechanism is different from what we pre-registered.**

For the paper §3.x:
- ✅ "SoA delivers 2.4× wall-clock speedup on synthesis-bound workloads with non-trivial alternation" (EXP-0002b)
- ✅ "The mechanism is cache locality + per-lookup cost, not heap pressure" (EXP-0002b-mem)
- ❌ "SoA reduces peak heap by ≥100 KB at synthesis-relevant scales" — falsified at grid_32x32 (76 KB observed)
- ⏳ "SoA's heap reduction scales with state count × num_fixpoint_vars" — testable in EXP-0002b-mem-deep at L4

This is a more precise, more defensible, more interesting story than the original. Honest falsifications strengthen the rest of the claims.

### Surprises / dead-ends

- *2026-05-06:* I expected the heap delta to be substantial because the iteration_ranks struct is the obvious memory difference. Empirically, iteration_ranks accounts for only ~76 KB at this scale; the rest of the 1+ MB heap is fixture data, formula AST, modal pre-image groups, etc. — none of which the SoA migration touches. Lesson: dhat is essential for this kind of mechanism attribution; intuition was wrong.
- *2026-05-06:* `cargo run --bin dhat_synthesis` failed at link time without `--features test_support,dhat`. The `[[bin]]` entry needed `required-features = ["test_support", "dhat"]` to gate it explicitly, otherwise `cargo build --bins` tries to build it with default features and breaks on missing `bench_support` and `dhat::Alloc`.
- *2026-05-06:* The dhat-mode binary runs ~5-10× slower than release mode (interception cost on every allocation). Wall-clock numbers from this binary are NOT comparable to Criterion bench numbers; only the heap profile is meaningful.
